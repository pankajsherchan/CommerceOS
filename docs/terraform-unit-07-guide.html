Terraform changes, explained step by step

1. Big Picture

The Terraform work added a minimal AWS development environment for CommerceOS. It does not deploy the app code yet. It creates the AWS places where future app containers will run.

Storefront

The Next.js storefront gets an ECR repository and an ECS service target. The ECS service currently runs zero tasks.

Commerce API

The FastAPI service gets its own ECR repository, ECS service, load balancer route, and database connection secret.

Database

PostgreSQL is created with RDS in private subnets. Only ECS tasks are allowed to connect to it.

Networking

A VPC, public subnets, private subnets, security groups, and an internet gateway are created for the dev environment.

Beginner translation: Terraform is creating the cloud skeleton. Later work will build Docker images and tell ECS to run them.

2. Terraform Basics

Terraform files describe the infrastructure you want. Terraform compares those files to real AWS infrastructure and then makes a plan to create, update, or delete resources.

  • resource means "create or manage this real thing," such as a VPC, RDS instance, or ECS service.
  • variable means "a setting someone can change without editing the main infrastructure code."
  • output means "print this useful value after Terraform runs," such as an ALB DNS name.
  • module means "reuse a bundle of Terraform files."
  • state is Terraform's local record of what it manages.

3. Folder Map

The new Terraform code lives under infra/terraform. It is split into reusable modules and one actual dev environment. 

infra/terraform/
  README.md
  modules/
    network/
    postgres/
    ecs-service/
  envs/
    dev/
      versions.tf
      variables.tf
      main.tf
      outputs.tf
      terraform.tfvars.example

Why split it this way?

Modules hold reusable building blocks. The dev environment chooses which blocks to use and wires them together. Later, a prod environment can reuse the same modules with different settings.

4. Resource Flow

Terraform determines the real dependency graph automatically, but it helps to read the code in this order.

1

Provider and inputs

versions.tf selects the AWS provider. variables.tf defines settings like region, database password, image URI, and desired task counts.

2

Network

The network module creates the VPC, public subnets, private subnets, route table, and internet gateway.

3

Container image homes

ECR repositories are created for the storefront and API. They are empty until a later CI/CD step pushes images.

4

Load balancer and security groups

The ALB accepts public HTTP traffic. Security groups allow the ALB to reach ECS tasks, and ECS tasks to reach RDS.

5

Database

RDS PostgreSQL is created in private subnets. The database URL is built and stored in Secrets Manager for the API task.

6

ECS services

ECS task definitions and services are created for storefront and API. They default to desired_count = 0, so no app containers run yet.

5. The Three Modules

modules/network

Creates the basic AWS network. Public subnets are for the ALB and dev ECS tasks. Private subnets are for RDS. There is no NAT gateway yet, which keeps this unit simpler and cheaper.

modules/postgres

Creates the RDS PostgreSQL instance, the database subnet group, and the security group that only accepts traffic from ECS tasks on port 5432.

modules/ecs-service

Creates an ECS task definition and service. It accepts the image, port, environment variables, secrets, target group, and networking inputs from the dev environment.

6. The Dev Environment

envs/dev/main.tf is the main composition file. It says how the modules and AWS resources connect to each other.

  • The storefront ALB target group listens on container port 3000.
  • The API ALB target group listens on container port 8000.
  • The ALB sends /health, /catalog*, and /cart* to the API.
  • Everything else goes to the storefront target group by default.
  • The API receives COMMERCE_API_DATABASE_URL from AWS Secrets Manager instead of a plain environment variable.
Important: both ECS services default to zero running tasks. That is intentional because this unit did not add Dockerfiles or build/push images.

7. Commands You Run

Format check

Checks that Terraform files use standard formatting.

cd infra/terraform
terraform fmt -check -recursive

Initialize Terraform

Downloads the AWS provider and prepares the dev environment folder. 

cd infra/terraform/envs/dev
terraform init

Create local variables

The real terraform.tfvars file is ignored by Git so it can contain local secrets like the database password. 

cp terraform.tfvars.example terraform.tfvars
# Edit terraform.tfvars and set db_password

Validate

Checks that Terraform understands the configuration.

terraform validate

Plan

Shows what Terraform would create in AWS without actually creating it. 

terraform plan

Apply

Creates the infrastructure in AWS. This can create AWS costs.

terraform apply

8. What Is Not Included Yet

This unit intentionally stops at a basic infrastructure baseline. These items are for later units:

  • Dockerfiles for storefront or API
  • building and pushing container images
  • Jenkins deployment automation
  • HTTPS, custom domain, and certificates
  • production environment
  • autoscaling
  • remote Terraform state
  • database migrations as a deployment step
