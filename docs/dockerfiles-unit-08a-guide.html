CommerceOS Unit 08A

Dockerfiles, explained step by step

This guide explains the storefront and commerce API Dockerfiles added for CI image publishing. It follows the files exactly and explains why each stage exists.

Sections

Big Picture Docker Basics Storefront Dockerfile Commerce API Dockerfile Dockerignore Files Build Commands

1. Big Picture

Unit 08A needs Jenkins to create deployable container images. The Dockerfiles define how to package each app so ECS can run it later.

Storefront

Builds the Next.js app with all development dependencies, then creates a smaller production image that runs next start on port 3000.

Commerce API

Installs the FastAPI service with production Python dependencies only, then runs uvicorn on port 8000.

Beginner translation: each Dockerfile is a recipe for turning source code into a self-contained runtime image.

2. Docker Basics Used Here

  • FROM starts a new image stage from a base image.
  • WORKDIR sets the folder where later commands run.
  • ENV sets environment variables inside the image.
  • COPY copies files from the build context or another stage.
  • RUN executes a build-time command and saves the result in the image layer.
  • USER makes the final container run as a non-root user.
  • EXPOSE documents the container port the app listens on.
  • CMD is the default command when the container starts.

Both files use multi-stage builds. Earlier stages can install tools or build code. The final stage copies only what the app needs at runtime.

3. Storefront Dockerfile

File: apps/storefront/Dockerfile

Full file

# syntax=docker/dockerfile:1.7

FROM node:22-alpine AS base
WORKDIR /app
ENV NEXT_TELEMETRY_DISABLED=1
RUN corepack enable && corepack prepare pnpm@10.26.0 --activate

FROM base AS deps
COPY package.json pnpm-lock.yaml ./
RUN --mount=type=cache,id=commerceos-storefront-pnpm,target=/pnpm/store \
    pnpm config set store-dir /pnpm/store && \
    pnpm install --frozen-lockfile

FROM base AS build
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN pnpm build

FROM base AS production-deps
COPY package.json pnpm-lock.yaml ./
RUN --mount=type=cache,id=commerceos-storefront-pnpm,target=/pnpm/store \
    pnpm config set store-dir /pnpm/store && \
    pnpm install --prod --frozen-lockfile

FROM node:22-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
ENV NEXT_TELEMETRY_DISABLED=1

RUN addgroup -S nextjs && adduser -S nextjs -G nextjs

COPY --from=production-deps /app/node_modules ./node_modules
COPY --from=build /app/.next ./.next
COPY --from=build /app/public ./public
COPY --from=build /app/package.json ./package.json
COPY --from=build /app/next.config.ts ./next.config.ts

USER nextjs
EXPOSE 3000

CMD ["node_modules/.bin/next", "start"]
1

Enable Dockerfile 1.7 syntax

# syntax=docker/dockerfile:1.7 enables newer BuildKit features, including cache mounts used by pnpm.

2

Create the shared Node base stage

FROM node:22-alpine AS base starts from a small Node.js Linux image. WORKDIR /app sets the application folder. NEXT_TELEMETRY_DISABLED=1 prevents Next.js telemetry during builds and runtime.

3

Install the package manager

corepack enable makes Corepack available, and corepack prepare pnpm@10.26.0 --activate pins pnpm for repeatable container builds.

4

Install all dependencies in the deps stage

The deps stage copies only package.json and pnpm-lock.yaml, then runs pnpm install --frozen-lockfile. This installs both production and development packages because the build needs TypeScript, Next.js build tooling, and other dev dependencies.

5

Use a pnpm cache mount

--mount=type=cache stores downloaded packages outside the image layer. Repeated builds can reuse that cache without copying it into the final image.

6

Build the Next.js app

The build stage copies node_modules from deps, copies the app source, and runs pnpm build. This creates the optimized .next production output.

7

Install production dependencies separately

The production-deps stage runs pnpm install --prod --frozen-lockfile. This gives the final image only runtime packages, not test or build tooling.

8

Create the runtime stage

FROM node:22-alpine AS runner starts a clean final image. It sets NODE_ENV=production so the app runs in production mode.

9

Add a non-root user

addgroup and adduser create a dedicated nextjs user. Running as non-root limits damage if the app process is compromised.

10

Copy runtime files into the final image

The runner copies production node_modules, .next, public, package.json, and next.config.ts. It does not copy tests, source control files, or local build artifacts.

11

Set the runtime command

USER nextjs switches away from root. EXPOSE 3000 documents the Next.js port. CMD ["node_modules/.bin/next", "start"] starts the production server.

4. Commerce API Dockerfile

File: services/commerce-api/Dockerfile

Full file

# syntax=docker/dockerfile:1.7

FROM python:3.12-slim AS base
ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1
ENV UV_COMPILE_BYTECODE=1
ENV UV_LINK_MODE=copy
WORKDIR /app

COPY --from=ghcr.io/astral-sh/uv:0.11.7 /uv /uvx /bin/

FROM base AS deps
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev --no-install-project

FROM base AS runner
COPY --from=deps /app/.venv ./.venv
COPY pyproject.toml uv.lock README.md alembic.ini ./
COPY alembic ./alembic
COPY src ./src
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev

ENV PATH="/app/.venv/bin:$PATH"

RUN useradd --create-home --shell /usr/sbin/nologin commerce-api && \
    chown -R commerce-api:commerce-api /app

USER commerce-api
EXPOSE 8000

CMD ["uvicorn", "commerce_api.main:app", "--host", "0.0.0.0", "--port", "8000"]
1

Enable Dockerfile 1.7 syntax

The syntax line enables BuildKit cache mounts for faster Python dependency installs.

2

Create the shared Python base stage

FROM python:3.12-slim AS base starts from a minimal Python image. The environment variables avoid .pyc writes during normal execution, keep logs unbuffered, ask uv to compile bytecode at install time, and make uv copy packages into the environment.

3

Install uv from the official image

COPY --from=ghcr.io/astral-sh/uv:0.11.7 copies the uv binaries into the Python image without installing uv through pip or a shell script.

4

Install production dependencies first

The deps stage copies pyproject.toml and uv.lock, then runs uv sync --frozen --no-dev --no-install-project. This installs locked production dependencies but skips the project package because source code has not been copied yet.

5

Use a uv cache mount

The cache at /root/.cache/uv speeds up repeated builds and stays out of the final image layers.

6

Create the runtime stage

The runner stage starts from the same base image, copies the virtual environment from deps, then copies project metadata, Alembic files, and application source code.

7

Install the project package

uv sync --frozen --no-dev runs again after source code is present. This installs commerce-api itself into the virtual environment without dev dependencies.

8

Put the virtual environment on PATH

ENV PATH="/app/.venv/bin:$PATH" lets the final command call uvicorn directly from the locked virtual environment.

9

Add a non-root service user

useradd creates commerce-api with a disabled login shell. chown gives that user ownership of /app.

10

Set the runtime command

USER commerce-api runs the app as the service user. EXPOSE 8000 documents the API port. CMD starts Uvicorn and binds to 0.0.0.0 so ECS can route traffic to the container.

5. Dockerignore Files

The .dockerignore files keep local-only files out of Docker build contexts. That makes builds faster and prevents local artifacts from accidentally entering images.

Storefront ignores

  • node_modules because dependencies are installed inside Docker.
  • .next because the container build creates a fresh production build.
  • .env* because secrets and local config do not belong in images.
  • coverage, test-results, and debug logs because they are local outputs.

Commerce API ignores

  • .venv because uv creates the virtual environment inside Docker.
  • .pytest_cache, __pycache__, and *.pyc because they are local cache files.
  • .env* because runtime secrets should come from the environment or AWS secrets.
  • dist and coverage folders because the Dockerfile builds from source.

6. Build Commands

These are the local image build commands used for Unit 08A verification. 

docker build \
  --file apps/storefront/Dockerfile \
  --tag commerceos-storefront:08a-local \
  apps/storefront

docker build \
  --file services/commerce-api/Dockerfile \
  --tag commerceos-api:08a-local \
  services/commerce-api
What success means: Docker can build both runtime images from the repository source. A later Jenkins run still needs to push those images to ECR.
